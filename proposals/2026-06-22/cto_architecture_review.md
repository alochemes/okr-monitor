# Architecture review — SQLite + ephemeral sandbox will break at 10 pilots

The decision to use SQLite in a cloud sandbox (§7, 2026-04-29) means every Sunday/daily run starts from an empty DB, making all rolling signal windows meaningless the moment real pilot data exists. Three High-severity risks in §9 have no corresponding mitigation KR in §3 Engineering pod.

## Risks
- **[HIGH]** `data` — SQLite DB is ephemeral in the remote sandbox (explicitly noted in §7 2026-04-29: 'SQLite DB in the cloud sandbox is ephemeral'), so signals_analyst 7d/30d rolling windows reset on every run — all KR verdicts are computed on a single run's events, not a real window.  
  → _Mitigation:_ Migrate the three signal tables (work_events, event_kr_mappings, kr_signals) to Supabase Postgres now; keep SQLite only for local dev. One Supabase project is already in the Sprint 0 entry checklist — wire store.py to DATABASE_URL env var with a Postgres adapter (psycopg2 or asyncpg), SQLite fallback when unset. (`2d`)
- **[HIGH]** `integrations` — Webhook idempotency exists at the schema level (UNIQUE source+source_event_id, §7 2026-04-29) but there is no retry/dead-letter path — a failed okr_mapper call on ingest silently drops the event with no requeue, so GitHub/Linear events that arrive during an LLM timeout are permanently lost.  
  → _Mitigation:_ Add a status column ('pending'|'mapped'|'failed') to work_events and a nightly sweep that re-queues rows stuck in 'pending' for >15 min; Inngest is already in the Sprint 0 checklist and is the right queue here — one job definition, 1 day. (`1d`)
- **[HIGH]** `security` — Slack ingestion privacy risk is listed as High in §9 with a DPA-by-2026-05-12 mitigation, but today is 2026-06-22 — that deadline is 6 weeks past and no DPA artifact appears anywhere in the tracker; onboarding pilots without a DPA exposes the company to GDPR/CCPA liability on every Slack-connected account.  
  → _Mitigation:_ Pause Slack integration for any new pilot until a one-page DPA (data processor agreement) is signed; use a standard SaaS DPA template (Bonterms or equivalent) — legal review is not required for a template. Gate the Slack OAuth flow in code behind a boolean requires_dpa_signed on the account row. (`1d`)
- **[HIGH]** `cost` — LLM cost scales with pilot count in a non-obvious way: the narrative agent ingests ALL mappings in a 7-day window per run, so a pilot with a noisy GitHub repo (500+ commits/week) will send a context window that costs 10-50x the dogfood baseline — at 25 pilots this could blow the $100/day circuit breaker mid-day and silence all other agents.  
  → _Mitigation:_ Cap events-per-KR fed to the narrative agent at 50 (configurable), selecting by highest confidence score; log truncation events to the audit log so the operator can see which accounts are noisy. This is a one-function change in agents/narrative/. (`1d`)
- **[MED]** `observability` — The Engineering pod KR 'p95 ingestion latency ≤2 min' (§3) has no queue choice recorded in §7 and no measurement infrastructure — there is no timestamp-delta between webhook receipt and kr_signals write, so this KR cannot be evaluated as true or false.  
  → _Mitigation:_ Add ingested_at and mapped_at timestamps to work_events (already has created_at presumably); the signals_analyst run can compute p95 of (mapped_at - ingested_at) and write it to a kpi_latency table read by the daily report. Schema change + one SQL window function, no new dependencies. (`1d`)
- **[MED]** `security` — OAuth tokens for GitHub/Linear/Jira/Slack/Notion are stored somewhere (Nango or direct, per Sprint 0 checklist) but there is no audit trail of which token accessed which customer's data — at SOC2-readiness KR (0/45 items closed, §3) this is a blocker for any enterprise pilot that asks for a security review.  
  → _Mitigation:_ Log every outbound API call (source, account_id, endpoint, timestamp) to the existing audit log (core/audit.py is already wired) — add a decorator or wrapper around each integration client. This is tech-debt acceptable until 20 pilots but must land before any SOC2 conversation. (`tech-debt`)
- **[MED]** `architecture` — The OKR-Mapper precision KR (≥85% P @ ≥70% R, KR1.3) is measured against a 50-event eval set built from dogfood data (agent proposals), but real pilot events are GitHub commits and Linear tickets — the eval distribution is completely unlike production, so the precision number will be optimistic by an unknown margin.  
  → _Mitigation:_ Before onboarding pilot #3, add 50 real events from at least 2 pilot accounts to dataset.py with human labels; retire the agent-proposal-only events to a separate 'synthetic' split so the headline metric reflects real data. Framework already supports this — it is a data entry task, not an engineering task. (`1d`)
- **[LOW]** `architecture` — kr_signals.json is written to web/public/ by the Python daily script and read by the Next.js dashboard at request time — this is a file-system coupling that breaks the moment the Python runner and the Vercel deployment are on different machines (which they will be after Vercel deploy).  
  → _Mitigation:_ Replace the file write with a Supabase upsert to a kr_signals table and replace the Next.js file read with a Supabase client fetch; this is the same Postgres migration as risk #1 and should be done in the same 2-day window. (`tech-debt`)
